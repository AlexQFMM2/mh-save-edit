## 已排除的资料阻塞

### 两层加密与校验

1. `SAVEDATA_PARAMS[0] = 0x41`，对应 PSP 加密模式 5。`BIN` 的文件 MAC 与 SFO 中的文件列表一致。
2. PSP 层解密后为 `0x16a100` 字节，包含 P2G 自身的替换／异或加密、SHA-1 和种子。
3. 现有 `mhef` 通用参考的存档替换表与本次已核验的 P2G 日版 BOOT 不同。直接调用参考库会失败，不能据此认定汉化版不兼容或存档损坏。
4. 原生 `0x088c2b80` 的读取路径与 `0x088c2dbc` 的写入路径均调用 `0x088c56bc`，明确给出各自的 256 字节替换表；种子初始化与更新分别在 `0x088c5890`、`0x088c58d0`。校验调用确认数据范围与盐的位置。
5. 使用这些原生表后，样本的游戏层 SHA-1 通过。保留原始随机信息时，重新编码的 **BIN 与原件逐字节一致**；明文为 `0x16a0e8` 字节。
6. 根据固定版本 PPSSPP 的校验顺序，SFO 同样可逐字节重建。本样本符合 PPSSPP 对未实现 fuse MAC 的既有回退行为；此结果不等同于已支持 PSP 实机的全部签名模式。

原生来源仍为宿主机已冻结的 P2G 日版 BOOT，SHA-256 与现有图鉴证据一致。仅返回有界指令摘要、两张必要查找表及地址，原始 BOOT 和完整游戏资源留在宿主机。由此确认当前汉化样本可按本作日版算法处理，而不是套用后作算法。

### 角色和正常装备身份

角色选择原生路径 `0x088c3294` 确认三个槽、`0x6b100` 步长、每槽起点相对存档块 `+0x1000`，并读取角色使用标记与性别。样本三个槽均已使用。

| 槽 | 明文起点 | 非空装备格 | 非空道具格 |
| --- | --- | --- | --- |
| 1 | `0x1000` | 12 | 0 |
| 2 | `0x6c100` | 108 | 601 |
| 3 | `0xd7200` | 160 | 988 |

P2G 装备记录为 12 字节，首字节是占用状态，第二字节是类型，`+2` 为本作装备编号，`+4` 为两字节的强化相关字段，后三个两字节字段为装饰品。角色已穿戴记录与装备箱记录分开存放。

原生名称与资料分派 `0x0885c960`／`0x0885ca48` 明确正常类型的对应关系；资料地址和记录步长可与已有图鉴原生表核对：

| 存档类型 | 图鉴原生表 |
| --- | --- |
| 0 | `armor_legs` |
| 1～4 | `armor_head`、`armor_chest`、`armor_arms`、`armor_waist` |
| 5 | `weapon_blademaster` |
| 6 | `weapon_ranged` |

**类型 0 是腿部，不能用 `saveType === 0` 判断空格。** 当前配装器的原生身份仍保持原样；正式存档适配应通过明确转换函数连接这些身份，不把正常图鉴 ID 全局改造成旧三作存档 ID。

本次样本的正常装备、道具和已安装装饰品可以关联已有图鉴。样本命中不能代替特殊记录、全部强化级别或全部原生编号的验证。

### 第二轮：装备同步与首批字段

用户确认继续使用现有解包与样本后，追加只读 BOOT／大厅 overlay 核查，证据、查询配置、复现脚本和验证结果保存在 `../research/mhp2g/save-followup-v1/`。第一轮归档保持不变。

- **穿戴按箱格引用同步。** 当前六件装备各有一个箱格编号，不能靠装备名称或记录内容相等寻找副本。原生 `0x088507ac` 写入引用，`0x08850854` 按引用复制箱内完整记录；工房修改后通过大厅 `0x09aa1668` 调用刷新。样本三个角色的全部有效穿戴引用和副本一致。
- **预设是 20 组箱格引用。** 大厅 `0x09adc570` 起的登记路径、`0x09ae5638` 的换位路径、`0x09ae5780` 的清理路径互相吻合。预设保存六个箱格编号及独立的颜色信息，不是六份装备记录。换位必须同步当前穿戴及预设引用；删除预设武器会清除该组全部六个引用，删除防具只清对应部位，颜色字节保留。原生删除函数拒绝删除当前已穿戴箱格。
- **强化字段必须按装备类别解释。** 防具防御读取路径使用 `+4` 的低字节强化次数，每次增加 2 防御并受本件原生上限约束；其他路径仍读取完整两字节，不能擅自清零高字节。弩的低四位是强化次数，原生升级到 4 为止，`0x10/0x20/0x40/0x80` 有独立标记更新路径；不能把整个数值显示为等级。弓虽然也属于存档类型 6，但攻击读取明确跳过弩强化逻辑。附件名称与全类别适用关系未全部核实，首批不提供猜测的附件选项。
- **箱体长度与开放容量分开。** 两类箱均保存 1,000 格；`0x08850d9c`／`0x08850e08` 根据两本收纳书的取得标记计算 800／900／1,000 格。不是检查道具箱里是否仍有这两本道具。未开放格的原字节仍需保留。
- **金钱、可消费点数和时间有原生读写证据。** 金钱由 `0x0884fae8` 增减，并用于买卖及带 `z` 的显示；点数由 `0x0884fb50` 增减，菜单显示为 `pts`；两者原生上限均为 9,999,999。时间由 `0x08850efc` 每 30 帧加一秒，原生上限为 35,999,999 秒。这些上限用于提示与正常输入，不能据此改写存量异常值。
- **HR 由任务标志推导。** `0x0884fbf4` 按指定任务的完成标志返回等级档，`0x08852dc8` 调用后加一供显示。任务 ID 还需通过原生索引表定位位号，不能直接把任务 ID 当位号。相邻累计点数字段不等于 HR；首批只显示推导结果，进度编辑另行接入。

新增 10 组离线修改／加密／SFO 重算／解密重读验证：金钱、点数、时间、已穿戴防具强化、卸珠并压紧、保持附件的弩等级修改、复制后编辑、带穿戴与预设的箱格移动、预设武器删除、预设防具删除。全部差分均限制在预期字段，其他角色、预设颜色及未知区域不变；另验证了拒绝直接删除已穿戴装备且不产生部分修改。测试用修改只存在于研究内存，未导回宿主机。

## 接入方式与顺序

使用现有存档工作区、角色选择、个人信息表单、道具箱／装备箱、详情、撤销和主进程会话。新增本作格式适配与必要的成对文件保存能力；不新建另一套编辑器页面，也不要求用户手工解密、计算校验或修补 SFO。

串行推进：原生字段和同步关系 → 本作 codec／adapter 与最小合成测试 → 会话的成对保存与故障恢复 → 原有 UI 的能力适配和图鉴／配装写入 → 四作回归与隔离样本游戏重开。未使用多代理，未提交、推送或发布。

存档源文件和会话明文分别是磁盘与草稿的事实来源；图鉴只解析稳定身份和显示资料。资料缺项不能使原始未知字节丢失，取消／撤销不得修改磁盘。多文件备份和回退是本作格式带来的必要复杂度。
